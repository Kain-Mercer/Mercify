# Developing Mercify

Technical notes for building and changing Mercify. Players don't need any of this; see the main [README](../README.md).

## How it fits together

```
 Spotify (SpotX + Spicetify)                 Mercify
 ┌──────────────────────────┐   ws://127.0.0.1:7317   ┌──────────────────────────────┐
 │ overlay-bridge.js        │ ──── now playing ─────▶ │ transparent, always-on-top    │
 │ (Spicetify extension)    │ ◀─── play / search ──── │ window covering your monitor  │
 └──────────────────────────┘                         └──────────────────────────────┘
```

- The Spicetify extension runs inside Spotify and talks to the client's own player, library and search. It doesn't use the Spotify Web API, so there's no developer app, no Premium requirement and no 10-result search cap.
- Mercify (Electron) runs the WebSocket server, draws the panels, and stays click-through everywhere except over a panel. While click-through, `pollCursor()` in `main.js` reads the cursor every 50 ms and the renderer says whether it's over a panel. Don't use `setIgnoreMouseEvents(true, { forward: true })`: on Windows it installs a system-wide low-level mouse hook on Electron's main thread, and every hiccup there stalled the game's mouse input (camera chug while steering in WoW, up to 1.13.1).
- A tiny native helper, `fgwatch.exe`, reports which window is in front so Mercify can show only over chosen games. It prints a JSON line on every change and every 2 s: `{"pid","hwnd","mon","exe","title"}`, where `mon` is the `MonitorFromWindow` handle. It also reports `cls` (window class). Writing `activate <hwnd>` to its stdin brings that window to the front (not if it's minimised: `SetForegroundWindow`, then attached to the foreground thread's input, then after a synthetic Alt tap, then `SwitchToThisWindow`) and prints `{"activate":<hwnd>,"ok":0|1,"via":...}`. Writing `anchor <hwnd>` adds `"anchor":{"hwnd","alive","iconic","visible","mon"}` for that window. It exits by itself when Mercify quits.
- **Gate:** `tickGate()` in `main.js` (every 200 ms). A chosen app in front opens the gate and becomes the anchor (`foreground.setAnchor`). Another app in front closes it, unless `onlyShowOver.stayOnOtherMonitor` is on and the anchor is up (alive, visible, not minimised) on a different monitor from the window in front. The Settings window in front closes the gate (so the overlay doesn't cover it) unless it's on another monitor from the anchor. Mercify's other windows and an unknown foreground leave the gate as it is. `reportGate()` sends Settings a plain-words reason (`settings:gate`). Gated hotkeys follow the game being in front (`gameInFront`), not the gate, so they're released while you use the other monitor. To test off Windows, `OVERLAY_DEBUG_FG_FILE` takes the same JSON plus `"windows":{"<hwnd>":{"alive","iconic","visible","mon"}}` for the anchor; `OVERLAY_DEBUG_STATE_FILE` reports `gateWhy` (`game`, `other-monitor`, `other-app`, ...). `tools/fg-test.js` (run in CI) drives `foreground.js` down its real Windows path against `tools/fg-fakehelper.js`, which speaks the helper's protocol; the debug-file path alone doesn't cover the parsing of real helper output. It also has two one-shot modes: `--hide <exe> <waitMs>` waits for that program's main window (visible, titled, unowned), hides it and prints `{"hidden":[hwnd,...]}`; `--show <hwnd>...` shows them again. Mercify uses these to send Spotify's window to the tray once the bridge first says hello (only within 2 minutes of Mercify starting, and only if `minimiseSpotify` is on), and for the tray's **Show Spotify window**.
- **SpotX detection** (`detectSpotX()` in `setup.js`): any of the backups SpotX's `run.ps1` makes in `%APPDATA%\Spotify` (`Spotify.bak`, `Spotify.dll.bak`, `chrome_elf.dll.bak`, `Apps\xpui.bak`), or its `// Patched by SpotX` line in `Apps\xpui\xpui.js` (where Spicetify unpacks `xpui.spa`). Not finding it is shown grey, not as an error, since it's optional and a custom `-SpotifyPath` install isn't checked.
- **One-click setup** (`setupAll()` in `setup.js`, Settings' **Set up everything**): SpotX (installs Spotify if needed), Spotify's first run (waits for its `prefs` file), Spicetify, the extension, then brings Spotify's window up (re-running `Spotify.exe` shows a minimised or tray-hidden window, where a login screen would otherwise stay unseen) and finishes. The **Connected to Spotify** row turns green on the bridge's `hello` (Spotify only loads the extension after you log in), with an **Open Spotify** button until then. Until 1.9.1 setup waited for that connection itself, holding the run (and the Redo buttons) for up to 30 minutes. Settings opened mid-run replays each step's progress (`setupRun.steps`). At startup, if setup is complete but Spotify hasn't connected 25 s after Mercify started it, its window is shown once. After the first login (through the browser), Spotify's window can stay blank and the extension never loads until Spotify restarts: once Spotify shows a login (`spotifyLoggedIn()`: an `%APPDATA%\Spotify\Users\<name>-user` folder, created straight away; the prefs file's `autologin` lines may only be written when Spotify closes, so 1.9.2's check never fired) and Spotify is running but hasn't connected, Mercify restarts it once per session (`restartSpotify()`): 8 s after a login it watched happen (setup's first login), 30 s if you were already logged in when it started, with a note on the **Connected to Spotify** row. Test hooks: `OVERLAY_DEBUG_FAKE_LOGGED_IN`, `OVERLAY_DEBUG_FAKE_SPOTIFY_RUNNING`, `OVERLAY_DEBUG_LOGIN_GRACE_MS`. Everything runs hidden; each step is checked against the disk, and a failure stops with a plain-words reason (`errorLine()` picks the telling line of the output) and **Try again** / **Copy details** in Settings. The step buttons became small **Redo** buttons, locked while anything runs.
  - SpotX's `run.ps1` is downloaded with Electron's `net.fetch` (saved with a byte order mark; Windows PowerShell 5.1 reads BOM-less scripts as ANSI) and run with every question pre-answered: `-confirm_uninstall_ms_spoti -confirm_spoti_recomended_over -block_update_on -podcasts_on -defender_exclusions_off -no_pause -new_theme`. If Spicetify has already changed Spotify (`Apps\xpui` but no `xpui.spa`), `spicetify restore` runs first, because SpotX refuses otherwise.
  - Spicetify is downloaded from its latest GitHub release (`spicetify-<v>-windows-<arch>.zip`) and unpacked into `%LOCALAPPDATA%\spicetify`, skipping its installer's questions (Marketplace, "fix your installation?", admin check).
  - PowerShell runs with `-NonInteractive -EncodedCommand` and TLS 1.2 enabled; any question we didn't foresee turns into an error that stops the run at once, it's stopped after 6 minutes without output, and the whole process tree is killed (`taskkill /T /F`). Until 1.9.0 the installers were spawned `detached` in their own windows, which didn't appear on some PCs (no console), so the buttons "did nothing".
  - Testing off Windows: `OVERLAY_DEBUG_FAKE_SETUP` (status) and `OVERLAY_DEBUG_FAKE_SETUP_RUN=ok|fail` (plays a run through the checklist).
- **Is Spotify installed?** `spotifyInstalled()`: `Spotify.exe` plus its app (`Apps\xpui.spa`, or the `Apps\xpui` folder Spicetify unpacks it into), *and* registered in Apps & features (`HKCU\...\Uninstall\Spotify`, written by Spotify's installer and SpotX; `spotifyRegistered()`). Windows' uninstaller leaves files it didn't install (Spicetify's unpacked app, files in use), and until 1.10.2 Mercify launched those leftovers at login, so Spotify ran with no trace in Apps & features. Leftovers (`Spotify.exe`, `.dll`s, `.bak`s, the `Apps` folder) are deleted by setup and by removal. Removal waits until every Spotify process has exited, retries locked files, and makes a second pass if Spicetify or SpotX is still detected. Uninstalling Spotify can leave `Spotify.exe` and SpotX's `.bak` copies behind; until 1.10.1 a lone `Spotify.exe` counted as installed (with nothing in Apps & features), and `removeAddons()` could even recreate one by putting SpotX's backups back onto an uninstalled Spotify. Now setup deletes such leftover program files before SpotX runs (`removeLeftovers()`, never `prefs` or `Users`), and `removeAddons()` only restores backups (and only runs `spicetify restore`) onto an installed Spotify.
- **Uninstalling:** `build/installer.nsh` (picked up by electron-builder) adds a `customUnInstall` step that asks whether to remove the add-ons, then runs `Mercify.exe --uninstall-cleanup` (Yes) or `--uninstall-cleanup=extension` (No) before the files are deleted. Never during an update (`${isUpdated}`) or a silent uninstall. That mode of `main.js` skips the single-instance check, runs `setup.removeAddons()`, writes `%TEMP%\mercify-uninstall.log` and exits. `removeAddons()`: closes Spotify; everything = `spicetify restore`, delete `%LOCALAPPDATA%\spicetify` and `%APPDATA%\spicetify`, drop Spicetify from the user PATH, put back SpotX's `.bak` files (what its `Uninstall.bat` does; the update block is a patch in those files), remove a leftover `Apps\xpui` folder, unlock an old SpotX-locked `Update` folder; extension only = `spicetify config extensions overlay-bridge.js-` + `apply`. Settings offers the same as **Remove Spicetify and SpotX…** (for the portable build).
- **Keeping Spotify out of sight during setup:** its first run (needed for Spicetify) starts it minimised with its window hidden, then closes it; Spicetify applies with `--no-restart` while Spotify is closed. The first time Spotify shows is the login at the end (or it starts hidden if you're already logged in). Spotify is always launched from its own folder (`launchSpotify()`). A login Mercify watches happen brings Settings to the front (`focusSettings()`: on top for a moment, plus the helper's `activate`), and restarts after it reopen Spotify minimised. After a restart Spotify gets 45 s to connect (1.11.0 judged it after 8 s), and there's at most one more restart.
- **Setup progress bar** (Settings header): an estimate, since setup can't know how long each step takes. Each step owns a slice of the bar (`PHASES` in `settings.js`; installing Spotify is most of it) and eases towards its end without going backwards; real numbers replace the guess where there are any (SpotX's download percentage, Spicetify's `Patching files [n/286]`, passed as `settings:setup-detail`). One plain line underneath says what's happening. It only belongs to an install run (from the button, or Settings opened mid-run, until it finishes or fails; `progRun`), so Spotify closing later doesn't bring it back. SpotX's download gets 4-30% (it's quick next to installing and patching), "Patching Spotify" lifts it to 45%. It ends as "All set!" once Spotify connects, red with the reason on a failure, or waits at 90% for you to log in. The raw log isn't shown any more; **Copy details** copies it (PowerShell's CLIXML noise filtered out).
- **Launch behaviour:** opened by the user, Mercify shows Settings. Started at Windows login it's launched with `--autostart` (registered via `setLoginItemSettings`) and stays in the tray unless setup needs attention. Spotify is started with its own `--minimized` flag.

## Building

**On GitHub:** every push to `main` runs the [Build Windows exe](../.github/workflows/build.yml) workflow on a Windows runner. To publish a release, bump `version` in `overlay/package.json` and push: when there's no `v<version>` release yet, the workflow publishes one with both exes, `latest.yml` and the installer's `.blockmap` attached. Other builds attach the same files to the run (Actions tab → the run → **Artifacts**). Changes to Markdown files and `docs/` don't trigger a build. Before releasing, the build runs `tools/check-package.js`, which fails if any `require()` in the packaged app points at a file or package that didn't get packaged. All top-level `overlay/*.js` files are packaged automatically.

## Updates

`overlay/updater.js` handles updates; installed copies use electron-updater with the GitHub provider (`build.publish` in `package.json`, which bakes `app-update.yml` into the app).

- **Launch splash (installer builds):** before anything else starts, `launchUpdateGate()` in `main.js` shows `splash/splash.html` (400x400, frameless; `assets/splash.png` is a copy of `docs/logo.png`, with the status line and bar in the dark band under the wordmark) and calls `updater.checkAtLaunch()` (8 s cap). No update, an error or a timeout: the splash closes (shown at least 900 ms) and startup carries on. An update: `waitForDownload()` shows the percentage (gives up after 60 s without progress and opens the current version), then "Installing…" and `installNow()` (silent install, starts the new version). Started with `--autostart`, the check is silent and the splash only appears for an update. The "update ready" notification is skipped during the gate. Test hooks: `OVERLAY_DEBUG_SPLASH=checking|downloading|installing` with `OVERLAY_DEBUG_SPLASH_CAPTURE=<png>` (screenshot and quit), and `OVERLAY_DEBUG_UPDATE_NO_INSTALL` (with `OVERLAY_DEBUG_UPDATE_FEED`: exit where the installer would run).
- **Installer builds** check the latest *published, non-prerelease* release 15 s after start and every 6 h. They read `latest.yml`, download the new `Mercify-Setup-x.y.z.exe` in the background (differentially via the `.blockmap` when the previous release has one), verify its SHA-512, and install silently when Mercify quits, or immediately with **Restart and update**, which relaunches the app.
- **Portable builds** (detected by `PORTABLE_EXECUTABLE_FILE`) only call the GitHub releases API and offer a download link.
- **Running from source:** updates are off.
- The exe isn't code-signed, so there's no publisher check on downloads (`publisherName` isn't set): integrity comes from the SHA-512 in `latest.yml` served over HTTPS from GitHub. Protect the GitHub account (2FA); anyone who can publish a release can ship an update.
- Releases must stay **published** (not draft or pre-release), and the release must include `latest.yml`, or installed copies won't see it. Don't rename release assets.
- Each release also carries fixed-name copies, `Mercify-Setup.exe` and `Mercify-portable.exe` (made by the build), so the README's download buttons can link to `https://github.com/Kain-Mercer/Mercify/releases/latest/download/Mercify-Setup.exe` and always get the newest version. They're extra assets: the updater only uses the versioned files named in `latest.yml`. For a release made without them, run the **Add fixed-name downloads to a release** workflow (`latest-links.yml`) from the Actions tab.

To test locally, serve a folder containing `latest-linux.yml` (the updater names its feed file after the OS it runs on; Windows uses `latest.yml`) and a matching exe, put a `dev-app-update.yml` (`provider: generic`, `url`, `updaterCacheDirName`) in `overlay/`, and run with `OVERLAY_DEBUG_UPDATE_FEED=<url>`. `OVERLAY_DEBUG_UPDATE_MODE=portable` with `OVERLAY_DEBUG_RELEASE_API=<url>` tests the portable check.

**Locally on Windows:** double-click `build-exe.bat`. The exes land in `overlay\dist`.

**From source** (Node.js 22.12 or newer; Electron 44 needs it):

```
cd overlay
npm install
npm start          # run from source
npm run demo       # (second terminal) a fake Spotify with a made-up library
npm run dist       # build the installer and portable exe into overlay\dist
```

`setup-and-run.bat` is the older all-in-one script that runs everything from source. `install-bridge.ps1` installs just the Spicetify extension by hand.

The helper is rebuilt with MinGW (`x86_64-w64-mingw32-gcc -O2 -municode -static -s -o bin/fgwatch.exe native/fgwatch.c`) or MSVC (`cl /O2 fgwatch.c user32.lib`). A prebuilt copy lives in `overlay/bin`.

## Listening lobbies

`overlay/lobby.js` (no Electron dependency) implements lobbies; `main.js` wires it to the bridge and the UI.

- **Transport:** MQTT over secure WebSockets to several public relays at once (`DEFAULT_RELAYS`: EMQX, Mosquitto, HiveMQ; HiveMQ can take 10+ s to connect). Every message is published to every connected relay and de-duplicated on receipt by `(sender id, sequence number)`. `lobbyRelays` in `config.json` overrides the list (for example with your own Mosquitto or EMQX).
- **Privacy:** topic = `mercify/v1/` + SHA-256(`"mercify-topic-v1:" + code`)[:32 hex]. Payloads are AES-256-GCM with a key from scrypt(code, `"mercify-lobby-v1"`, N=16384). Anyone with the code can read and join; others see random topics and ciphertext. Codes are normalised to A-Z/0-9 (4-16 characters); generated codes are 8 characters from a 31-letter alphabet.
- **Messages:** `hello` (joining), `here` (heartbeat every 8 s, carries role), `bye`, `state` (host only: uri, position, playing, sentAt; on every change, on seeks and every 5 s), `ping`/`pong` (clock offset to the host, median of recent samples, re-measured when the host changes), `suggest` (to the host, queued with `addToQueue`).
- **Roles:** a joiner listens for 2.5 s; if no host answers, it becomes host. Host = earliest `joinedAt` (each member's own clock), ties by id; everyone computes the same answer, so host hand-over on `bye` or a 25 s silence needs no negotiation, and two simultaneous hosts resolve themselves.
- **Session playlist:** the host owns `queue` (up next), `history` (played, newest first) and `now` (the queued item playing, so its "added by" shows) and broadcasts them in a `queue` message on every change, to newcomers, and every 15 s. Listeners add with `suggest` (track info; the host builds the item with the sender's name/id), or a whole album/playlist with `suggest-many` (`items` in order plus a `label`, one message so relays can't reorder the songs, one notification; the host keeps what fits under `QUEUE_MAX`, 100) and remove their own items with `queue-op`. Items from the network are rebuilt by `makeItem` (URI pattern, https-only images, length limits). The host plays the next item 350 ms before the current song ends (`scheduleAdvance`). While the list has songs it's in charge: any song change the host's Spotify makes on its own (its next song, crossfade or Automix starting early) is replaced with the next item, unless the host picked the song in Mercify within the last 4 s (`markManual`, called by `main.js` for overlay `playTrack`/`playContext`/`next`/`prev`). If Spotify happens to move on to exactly the next item, it's taken as played. The host's Next plays from the list when it isn't empty. A new host carries on with its copy of the list.
- **Session playlist when solo:** outside a lobby the Session Playlist panel shows Spotify's own Up next instead: the extension sends `queue` (`next`: up to 50 of `Spicetify.Queue.nextTracks`, without autoplay suggestions, each with `queued` when you added it) on every song change and whenever it changes (checked every 2 s). Songs you queued show "You" and can be removed (`removeFromQueue`). **Played** lists the songs played since Mercify started, from the `state` messages. Joining a lobby swaps in the lobby's playlist; leaving swaps back. `npm run demo` sends a queue too.
- **Copying the code for WoW chat:** `copyLobbyCode()` (overlay button, Settings, tray, starting a lobby) puts `[Mercify:CODE]` on the clipboard when WoW is in front (`wowInFront()`: the foreground window matches `onlyShowOver`, or the overlay itself is focused over the game), otherwise the plain code. K-UI: Forever (1.0.302+) shows that bracket in chat as a link that copies just the code. `normalizeCode()` takes the code out of a pasted `[Mercify:...]`.
- **Vote skip:** listeners send `vote` (`uri` of the song playing, `on`) to the host; the host keeps `skipVotes` (member id -> uri), drops votes for other songs or from people who've left, and skips with `playNext()` once votes >= ceil(members / 2), so ties skip. The tally goes out as `skip` in the `queue` message (`{ uri, voters, need, total }`), a `skipped` message tells everyone, and votes reset on every song change and host change. It's recounted when someone joins or leaves, so a leaver can tip it over. A listener's Next button and Next hotkey are votes too (`voteSkipFromNext()` in the renderer, `hotkeyActions.next` in `main.js`); the host's Next plays the next session song. Only the playing song can be voted on; the Now row shows the host's song even when it isn't from the session playlist (`current` in the lobby state).
- **Throttled Spotify:** after Spotify's window has been hidden for about five minutes (in the tray, or behind the game), Chromium runs the page's timers only about once a minute, so the extension's own `state`/`progress` reports nearly stop. Commands still arrive straight away, so `main.js` asks for `state` itself whenever nothing has come in for 2.5 s, and 350 ms after every playback command (`askSpotifyState`). Before this, lobbies drifted apart during long autoplay sessions until someone opened Spotify's window. `tools/mock-bridge.js` reproduces it with `MOCK_THROTTLE=1` (plus `MOCK_DURATION`, `MOCK_START`, `MOCK_STEP`, `MOCK_LOG_CMDS`).
- **Following:** listeners play the host's song, seek to the host's position (adjusted by the clock offset), match play/pause, and re-seek when more than 2 s off. Host messages are applied immediately; the listener's own player reports are ignored for 1.5 s after a correction, and out-of-order host messages are dropped.
- **Leaving:** every leave you start (Lobby panel, Settings, tray) goes through `leaveLobby()` in `main.js`, which pauses Spotify afterwards if you were in a lobby (it asks the extension for fresh `state` first and sends `togglePlay` only when it's playing, so no extension update is needed). Cancelling while connecting and quitting Mercify don't pause.
- **Starting outside the overlay:** Settings' Lobby page (`settings:lobby-start`, `settings:lobby-join`, `settings:lobby-copy`) and the tray's **Start a listening lobby** (`startLobbyFromTray`). Start joins a fresh `generateCode()` code (so you're the host) and copies it to the clipboard (`startLobby()` in `main.js`). Both need a name first; the tray opens Settings on its Lobby page (`openSettings("lobby")`) with a notification if there isn't one. While connecting, the tray shows the code with **Cancel**.
- **Testing:** `tools/lobby-test.js` runs three members in separate processes with clocks up to 7 s apart against real relays (`LOBBY_RELAYS=ws://127.0.0.1:9001,...` for local Mosquitto instances), covering sync, seek, pause, song change, suggestions, losing a relay, encryption, host leave and host crash. The [Check lobby relays](../.github/workflows/lobby-relays.yml) workflow runs it against the public relays weekly and on demand, and reports each relay as a run annotation.

## Friends

`overlay/friends.js` (no Electron dependency) keeps a friends list across sessions; `main.js` wires it to the lobby, the bridge and the UI.

- **Identity:** each install has an X25519 key pair in `friends.json` (next to `config.json`), with the friends list (`{ v, identity: { pub, priv }, friends: [{ fid, pub, name, addedAt }] }`). The friend id (`fid`) is SHA-256(`"mercify-fid-v1:"` + raw public key)[:16 hex]. Lobby `hello`/`here` messages carry `fpub`, so every member's `fid` is in the lobby state (older versions send none: "needs a newer Mercify").
- **Adding:** right-click a lobby member (`contextmenu`; with the click zone on, the helper reports a right click in the zone as `{"zone":"context"}` on release) → `friends:add` → `friends.startAdd()` and a lobby `friend-add` to that member (with `to`). The other side gets a request (`add-request`; Notifications, Friends panel, tray) and answers with lobby `friend-ok`/`friend-no`. Accepting also sends `ok` on the pair channel, which the requester listens on from the moment it asks, so the answer still arrives if it left the lobby. Asking someone who's asked you accepts. Requests you send are forgotten after 10 minutes.
- **Pair channel:** key = HKDF-SHA256(X25519 shared secret, salt `"mercify-friend-v1"`, info `"key:" + sorted fids`), topic = `mercify/v1/` + HKDF(…, `"topic:…"`, 16 bytes) as hex. AES-256-GCM like lobbies. Messages carry `f` (sender fid), `b` (a random id per run) and `n`, de-duplicated by `(b, n)`. Same relays as lobbies (`lobbyRelays`), separate connections, only opened once there's a friend or a request out. Messages sent with no relay connected wait (up to 2 minutes).
- **Messages:** `p` presence (name, `share`, `track` `{uri,name,artists}` only when sharing, `playing`, `lobby`, `host`, `join`; `ask: true` asks for theirs back) every 30 s and 1.2 s after a change; `off` on quit; offline after 75 s without one. `jreq`/`jok` (with the lobby `code`)/`jno` (`why`: `declined`, `off`, `timeout`, `error`)/`jcancel` for joining; `unf` when removed; `ok` for friend requests.
- **Request to join:** `friends:request-join` → `jreq`. The friend gets `join-request` (Notifications panel card with buttons, Friends panel, tray submenu, and a Windows notification while the gate is closed or the overlay hidden). It expires after 60 s. Accepting runs `codeForFriend()` in `main.js`: the lobby you're in, or a new one (`generateCode()`); the code goes back in `jok` and the requester's `main.js` joins it. After a refusal the requester waits 15 s before asking that friend again.
- **Profile pictures:** Settings' circle next to your name (`settings:pick-avatar`) crops the picked image to a square and saves a 96x96 JPEG (quality stepped down until it's under 12 KB) as `avatar.jpg` next to `config.json`. A picture with any transparent pixels (alpha under 250) is instead trimmed to its visible part, padded to a transparent square (`transparentSquare()` in `main.js`) and saved as a PNG, `avatar.png` (96 px, or 80/64/52 if needed to stay under 17,500 bytes, which keeps the data URL inside `cleanAvatar()`'s limit); JPEG would turn the background black. Only one of the two files exists at a time, and the PNG wins at startup. The overlay and Settings show a PNG picture with class `clear`: no coloured disc, not clipped to a circle, `object-fit: contain`. Older versions already accept PNG pictures, so they show it too (on their disc). Lobby `hello`/`here` carry `avh` (SHA-256 of the data URL, 12 hex; `""` for none); the picture itself (`av`) goes with `hello`, with the `here` answering a `hello`, and to the whole lobby when it changes; a member whose `avh` doesn't match what we have is asked with `av-ask` (at most every 30 s). Friends' presence carries `avh` too, answered with `avq` → `av`, and friends' pictures are kept in `friends.json` for when they're offline. `cleanAvatar()` (in `friends.js`) only lets through `data:image/(jpeg|png|webp);base64,` up to 24,000 characters.
- **Lobby panel size:** `fitLobby()` in the renderer grows the Lobby panel (never shrinks it, and not in Edit Mode) until up to 4 members fit without scrolling; with more, the member list scrolls. It grows away from the nearest screen edge, isn't saved to the layout, and gets `.grown` (drawn above a neighbouring panel it now covers).
- **Clickable notifications:** the Notifications panel is `passive`, except cards with buttons (`actionToast()`, `.notice.actionable`): those take clicks even while the overlay is hidden, and only their rectangles join the click zone. They're closed when main's `requests` no longer has them.
- **Testing:** `tools/friends-test.js` runs three installs (friends + lobby each) against in-memory stand-in relays (`connect` option on `createFriends` and `createLobby`), so it runs on every build: requests (accept, decline, answer after leaving), presence, sharing off, request to join (new lobby, existing lobby, decline, turned off), remove, restart, going offline, and that relays only see ciphertext.

## YouTube

`overlay/youtube.js` (no Electron dependency) fetches YouTube audio with yt-dlp; `main.js` plays it and fits it in with Spotify.

- **yt-dlp:** the official standalone exe (`yt-dlp.exe` from its latest GitHub release) is downloaded into `%APPDATA%\Mercify\yt-dlp` the first time a video is needed, and updated with `yt-dlp -U` at most once a day, before the next use (`state.json` remembers when). Settings' Setup page shows its version, with **Update yt-dlp**.
- **JavaScript runtime:** since 2025.11.12 yt-dlp needs one for YouTube. Mercify's own executable is one: run with `ELECTRON_RUN_AS_NODE=1` it's Node (24 in Electron 44), passed as `--js-runtimes node:<process.execPath>`. yt-dlp runs it as `<exe> --permission -` with its script on stdin. Deno, if installed, still comes first (yt-dlp's own order). This relies on Electron's `RunAsNode` fuse staying on (electron-builder leaves fuses alone unless `electronFuses` is set).
- **Links and lookups:** `parseId()` takes watch, `youtu.be`, shorts, embed, live and music.youtube.com links (not bare ids, which look like words). Titles come from YouTube's oEmbed (fast, no length), falling back to `yt-dlp -J`; search is `yt-dlp -J --flat-playlist ytsearch8:<query>`. Thumbnails are `i.ytimg.com/vi/<id>/mqdefault.jpg` (16:9, no black bars).
- **Playing:** the audio is downloaded whole before it plays (`bestaudio`, webm/opus or m4a, a few MB) into `%TEMP%\Mercify YouTube`, then played from the file by `player/` in a hidden window (`backgroundThrottling: false`), through a Web Audio compressor that evens out loudness (YouTube uploads vary far more than Spotify's). Pasting a link starts the download straight away. When YouTube answers "Please sign in" (it refuses some videos, often big labels' music videos, to yt-dlp's default clients), the lookup or download is tried once more with `--extractor-args youtube:player_client=tv_simply,web_embedded,mweb,android_vr` (`FALLBACK_CLIENTS`), which need no account either; diagnostics log which way it went. Once the other clients were needed, they go first for 6 hours (`othersFirstUntil` in `state.json`; YouTube tends to treat a connection the same way for a while), so each video doesn't waste a failed attempt. The cache drops files older than two days or past 300 MB, never the one playing. The same video asked for twice shares one download. Fetching ahead (`prepare(id, { background: true })`: the session playlist, the top two YouTube search results, and a result the mouse rests on for 300 ms, which goes to the front) runs one at a time; a video you play starts at once, taking over its download if it's still waiting.
- **One player at a time:** a video is `youtube:<id>` everywhere (overlay, Settings, lobby, friends), with a state shaped like Spotify's plus `source: "youtube"` and `loading`. Every playback command goes through `playerCommand()` in `main.js`: YouTube URIs and, while a video is current (`yt.active`), play/pause, seek, volume (`config.youtubeVolume`) and Previous go to the YouTube player; Next ends the video and moves Spotify on; shuffle, repeat and like are refused. Spotify is paused when a video starts and its reports are held back (`spotifyInCharge()`), unless it starts playing by itself after a 5 s grace (you pressed play in Spotify), which ends the video. When a video ends, a lobby host's session playlist plays its next song; otherwise Spotify carries on if it was playing before the video.
- **Lobbies:** `URI_RE` in `lobby.js` accepts `youtube:<id>`, so videos go through the session playlist, the host's state and following like songs. Every member downloads the current video and the next four in the session playlist ahead (`prefetchLobbyVideos()`, on every lobby change; a failed one isn't retried for 10 minutes), so the host's "play this at 0:42" finds a local file. Older versions reject YouTube items.
- **Discord:** Spotify's own Discord card disappears while a video pauses Spotify, so `overlay/discord.js` shows Mercify's own Rich Presence through the Discord app's local pipe (`\\?\pipe\discord-ipc-0`..`9`; no library, no OAuth), as the Discord application "Mercify" (`DISCORD_CLIENT_ID` in `main.js`, set up by Kain on the Developer Portal). Every player state passes through `discord.update()` from `emitPlayer()`: a playing (not loading) YouTube video is a Listening activity (type 2) with `status_display_type` 2, so the member list reads "Listening to <video title>"; the card has the channel ("by …"), the thumbnail (an external URL), start/end timestamps for the progress bar and a "Watch on YouTube" button (shown to others, not yourself). Anything else (paused, Spotify, nothing) clears it, and Spotify's card comes back by itself. Updates are skipped when only the position moved (under 3 s off), spaced at least 4.5 s apart (Discord allows 5 per 20 s), and collapse to the latest. Mercify connects only while a video plays, retrying every 20 s (sooner on a new video) if Discord isn't running; Discord drops the card itself when Mercify quits. `config.discordYouTube` (Settings' Friends page and Home's quick settings, default on) turns it off. `tools/discord-test.js` (run in CI) checks it against a stand-in pipe.
- **Testing:** `OVERLAY_DEBUG_YTDLP=tools/fake-ytdlp.js` swaps yt-dlp for a stand-in that answers lookups and searches and "downloads" a tone (`FAKE_YT_SECONDS`, `FAKE_YT_DELAY_MS`; ids starting `unavailabl` fail, `signinonly` need the other clients, `signinalway` always ask to sign in). `tools/youtube-test.js` (run in CI) covers links, lookups, search, shared downloads, the cache, errors and a video passing through a lobby.

## Settings window

`settings/` is Mercify's own window (1000x660, resizable): a sidebar with six pages (Home, Lobby, Overlay, Hotkeys, Setup, General) in one of four themes.

- **Themes:** every colour and type choice is a CSS variable set per theme on `<html data-theme>` (`settings.css`); the components only use the variables. Classic (the default) keeps the old window's colours; Neon, Light and Vice are the others. `config.theme` is passed in the address (`?theme=`) and as the window's background colour (`THEME_BG` in `main.js`), so the first frame is already in the right theme. Vice's palm tree is `settings/vice-palm.svg`. The overlay follows the same theme: `renderer/style.css` names every colour by its role (`--surface`, `--track`, `--ghost`, `--play-bg`, ...), with Classic's values being the overlay's colours before themes, and one block per theme overrides them (no decorations in the game, just colours, fonts and a faint glow for Neon and Vice). The overlay gets the theme in its address at start and as `theme` when it's changed in Settings. Edit Mode's amber and the snapping guides are the same in every theme (Light uses a darker amber for Edit Mode's text). Fonts are bundled in `settings/fonts/` (Latin subsets from Fontsource, SIL OFL, see its `LICENSE.txt`), since the window can't load from the web.
- **First run:** while Spotify, Spicetify or the extension is missing (`wantFirstRun()` in `settings.js`), the window is the installer: the four steps, the **I have Spotify Premium** tick (the only place it's asked; afterwards the extension reports the plan) and one button. It stays until **Open Mercify** or **Not now**, so a run can be watched to the end. Anything else that needs fixing (an outdated extension, SpotX in the wrong mode) shows as a dot on **Setup** and **Needs attention** on Home, with **Finish setup** on the Setup page. Both views share one step model and progress bar.
- **Now playing:** `main.js` forwards the bridge's `state`/`progress` to Settings (`settings:player`, kept as `settingsPlayer`), and Home's buttons go through `settings:player` (`SETTINGS_PLAYER`), which behaves like the overlay's: in a lobby, a listener's Next votes to skip and the host's plays the next session song.
- **Hotkeys:** **Change** listens for the next key combination. Meanwhile `suspendHotkeys(true)` releases every global shortcut (a registered one goes straight to its action and never reaches the window); Esc, another page, the window losing focus or closing brings them back. `setHotkey()` refuses a combination already used by another hotkey, one Windows won't register (another program has it: it tries `globalShortcut.register` first), and, in the page, a plain key without Ctrl or Alt (F-keys and media keys are fine), so typing in the game isn't taken over. Changes apply at once.
- **Opening on a page:** `openSettings("lobby")` shows a page (the address's `?page=`, or `settings:page` when the window is already open).
- **Testing off Windows:** `OVERLAY_DEBUG_SETTINGS_CAPTURE` with `OVERLAY_DEBUG_SETTINGS_JS` (awaited, so it can be an async function that clicks through pages: `document.querySelector('.nav[data-page=hotkeys]').click()`), `OVERLAY_DEBUG_FAKE_SETUP` for the steps (`{"supported":true,"spotify":false,...}` shows the first-run screen), and `npm run demo` for something playing.

## Window size

While shown or in Edit Mode, the overlay window is sized to the chosen display's full `bounds`, taskbar area included. While hidden it only covers the panels whose "opacity when hidden" isn't 0 (the renderer reports them as `hidden-area`, in display coordinates), plus 24 px for shadows, and it's hidden entirely when there are none. A full-screen window on top of a game, even a see-through one, makes Windows composite every game frame with it instead of letting the game present directly (160 → 90 FPS, worst after alt-tabbing back in). The renderer always lays panels out in display coordinates (`dispW`/`dispH`, never `innerWidth`) and shifts the page by the window's offset on `viewport`; growing, it applies the offset first and answers `viewport-applied` before the window grows, so visible panels don't jump. `placeWindow()` sets the bounds after every show (and 400 ms later), when the overlay is shown or hidden (250 ms after hiding, once panels have faded), when Edit Mode starts, on display changes, and in the 200 ms gate check: Windows pulls a window larger than the work area back inside it when it's shown. The gate check gives up after 4 tries in a row so it can't fight Windows forever, and logs it; **Copy diagnostics** shows the window, display and work-area sizes. `OVERLAY_DEBUG_SHRINK=<ms>` shrinks the window by 40 px after start, to test this off Windows.

## Focus and click-through

The overlay window stays `focusable: true`: on Windows, Chromium discards clicks on a window that can't be activated (`focusable: false` caused the 1.3.0 "can't click anything" bug). Clicking a panel therefore activates the overlay, and the renderer then sends `give-back-focus` about 120 ms after any click that didn't land in a text box. `giveFocusBack()` asks the helper to `activate <hwnd>` the last window in front that wasn't ours (`lastOtherHwnd`, normally the game) and waits for its answer (`{"activate","ok","via"}`: `set`, `attach`, `alt`, `switch`, or `minimised`/`gone`/`none`). While it waits, and until that window shows up in front (at most 1.5 s), other windows that flicker past don't close the gate or become `lastOtherHwnd`. If Windows refuses, the overlay stays up and keeps the keyboard, with a toast asking you to click the game. `win.blur()` is only used without a helper: it activates the next *visible* window below the overlay in z-order, which for an always-on-top window is often another topmost or invisible one (the taskbar, an input-method window), so the gate hid the overlay and the game had no keyboard (1.7.0 and 1.7.1 on single-monitor PCs; 1.7.1 still called `blur()` 300 ms after a successful activate whenever Electron reported the overlay as focused). The taskbar and Start menu (`Shell_TrayWnd`, `Shell_SecondaryTrayWnd`, `Windows.UI.Core.CoreWindow`) are treated like Mercify's own windows by the gate. Text boxes keep focus until `Enter`/`Esc` or a song is picked (`releaseFocus()`), and the search hotkey and the playlist filter use `takeFocus()` via `want-focus`. Click-through is decided per mouse move in the renderer; while hidden, only the Now Playing panel (`.live-hidden`, full or compact; `liveHidden` in the layout, on unless unticked) takes clicks.

**Click zone (no keyboard grab on clicks).** Activating the overlay makes the game drop every held key, so a click on a panel while running with WASD stopped the character. So while the gate is open and the overlay window doesn't have the keyboard (not Edit Mode, no text box focused), the window stays click-through and the helper takes the panels' clicks instead: the renderer sends the rects of the panels that take clicks (`click-zone`: every visible, non-passive panel while shown; only Now Playing while hidden, if `liveHidden`; plus notification cards with buttons, shown or hidden), `syncZone()` in `main.js` converts them to physical pixels and writes `zone <x> <y> <w> <h> ...` (up to 16) or `zone off` to the helper. The helper then runs a `WH_MOUSE_LL` hook on its own thread (only while a zone is set; the callback only checks the rects and queues a line for a writer thread, never waiting on Mercify): a left press inside the zone is kept from the game and reported with its drag and release (`{"zone":"down"|"move"|"up"|"cancel","x","y"}`, moves at most every 15 ms), a wheel notch as `"wheel"` with `d`, and right clicks in the zone are kept from the game and reported on release as `"context"` (replayed as a `contextmenu` event, for the lobby and friends menus). While the cursor is hidden (the game is steering the camera) or the other button is held, everything passes through. `main.js` sends these to the renderer (`zone-mouse`), which replays them: synthetic `pointerdown`/`pointermove`/`pointerup` on sliders, `click` when press and release land on the same button or row, `wheel` (and scrolls the list itself, since replayed wheel events don't scroll), dragging a list's scrollbar, and a press on a text box asks for the keyboard (`want-focus`; with the zone on, `main.js` has the helper bring the overlay to the front first, since Windows won't let Mercify take it without having had the click). Hover effects use the `.zh` class on everything under the cursor (each `:hover` rule in `style.css` has a `.zh` twin) plus synthetic `mouseenter`/`mouseleave`, from the cursor polling. Without the helper the old path (window clickable under the mouse) is used. `tools/fg-test.js` covers the protocol.
